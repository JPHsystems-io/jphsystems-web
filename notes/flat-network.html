The flat network is still the default

One VLAN, one subnet, a firewall at the edge, and a VPN that lands you inside it. It is the default because it works, right up until one laptop is compromised.

JPH JPHsystemsFounder & engineer

A flat network is not a mistake anyone consciously makes. It is what you get when a switch is installed, a subnet is chosen, and every device that arrives afterwards is plugged into the same place. The firewall blocks inbound traffic from the internet. Inside, everything can talk to everything.

That design survives because it is convenient: file shares work, printers appear, and the line-of-business app connects to its database without a ticket. The cost only shows up on the day an attacker gets one set of credentials and finds that the laptop in reception can reach the domain controller, the file server and the backup appliance.

What flat actually means

In practice, a flat network usually looks like this: workstations, servers, printers, cameras, the phone system and the backup target all share a /16 or a handful of /24s. The VPN hands remote users an address on the same plane. The firewall is a perimeter device; it has almost no opinion about traffic that stays inside.

So one phished session becomes a network position. An attacker does not have to exploit the server when they can simply log into it with credentials lifted from the laptop, and they do not have to break the backup at all if the backup share is mounted and writable from a machine they already control.

Why it stays that way

  • Nobody has an accurate diagram. The network changed, the documentation did not, and nobody wants to touch a design they cannot see.
  • Fear of breaking the app. Segmentation sounds like an outage, so it gets postponed until after the busy quarter that never ends.
  • The firewall is in the wrong place. It is treated as an internet boundary, not an internal policy point, so east-west rules are never written.
  • It has always worked. A control that has not failed yet feels like a control that cannot fail.

The order that gets finished

Segmentation fails when it is planned as a big-bang redesign. It works when it is a sequence of small, reversible changes, each one with a reason and a rollback. This is the order I use.

  1. Inventory and diagram. What exists, what talks to what, and which flows are actually required. Start with the traffic, not the VLAN plan.
  2. Move the management plane out. Switch and firewall admin, hypervisor consoles, iLO/iDRAC, NAS management. Put them on a separate management network behind a jump host with MFA.
  3. Isolate the backups. Separate credentials, separate network path, and at least one copy that the production estate cannot write to. Ransomware goes for the backup first because it makes recovery optional.
  4. Fix guest and Wi-Fi. Guest to internet only. Corporate Wi-Fi to the services people need. Cameras, door controllers and other appliances on their own segment with no route to user devices.
  5. Group by function. Servers, databases, workstations, development and the management plane. Name the zones by what they do, not by which switch they happen to be on.
  6. Log before you block. Turn on flow logs and firewall logging for a week. You are looking for the flows nobody remembered: the scanner, the backup job, the one consultant with a mapped drive.
  7. Deny by default between zones. Allow only the flows the diagram requires, by service, source and destination. Every rule gets a name, an owner and a review date.
  8. Document the exceptions. The exception is not the failure. The undocumented exception is.
The one rule that matters: between zones, deny by default. If you cannot explain why a rule exists, that is a finding, not a requirement.

Start with one path

You do not need a maintenance window and a new firewall to begin. Pick one path that should not exist: a workstation reaching the NAS management interface, a laptop reaching the database port, a camera reaching a file share. Put a deny rule in front of it, log what happens, and see what breaks.

If nothing breaks, you have removed a path an attacker would have used. If something breaks, you have found a dependency that was invisible before. Both outcomes are progress. Do that five times and you have a segmentation programme that is already paying off.

What good looks like

  • A user can reach the application, not the database behind it.
  • A vendor can reach one host for one agreed window, with a named sponsor.
  • A camera can reach the recorder and nothing else.
  • A backup server accepts connections from the backup job and refuses everything else.
  • The diagram matches the equipment, and somebody owns the difference when it does not.

None of that needs a new product. It needs a boundary, a rule, and someone disciplined enough to write down why the boundary is there. That is the boring part, and it is the part that holds.
