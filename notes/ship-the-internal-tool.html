Ship the internal tool

The spreadsheet with three owners and no tests is costing more than the app you keep postponing. It is also already software, with none of the safeguards.

JPH JPHsystemsFounder & engineer

Every operations team has one. A spreadsheet that became a system: a workbook with macros, a colour code, a tab called FINAL_v3, and three people who know how it works. One of them is leaving, or already has.

The tool is not the problem. The problem is that the business now depends on logic that lives in cells, permissions that live in a file share, and history that lives in whoever remembers to save a copy before the month closes.

The spreadsheet is already software

It has an interface, a data model, business rules and an access model. What it does not have is version control, tests, an audit trail, or a way to run the same rule twice and get the same answer. It fails silently: a deleted row, a formula dragged one column too far, a hardcoded value that nobody notices until the numbers stop reconciling.

The cost is not the licence. It is the reconciliation hours, the onboarding that only happens by shadowing, the errors found a quarter late, and the audit question you cannot answer because the evidence was overwritten.

Why the app keeps getting postponed

  • It works well enough on a good day. The failure is invisible until month-end, so it never becomes urgent.
  • Internal tools do not demo well. There is no launch video for “the job list now has an owner field”.
  • “We’ll buy something.” Then procurement takes six months and delivers a platform that fits 70% of the workflow and none of the exceptions.
  • Scope creep at the first draft. SSO, role-based access, mobile, audit, reporting and an AI assistant, before anyone has agreed what the tool actually does.

Scope it like an incident, not a platform

The smallest useful version has one workflow, end to end, and one source of truth. Concretely:

  • One workflow. A form to create a record, a list to see it, and a state change to close it. That is the application.
  • One database. Not a shared drive, not a synced folder, not a second spreadsheet that “mirrors” the first.
  • One import. Bring the existing data across once, and produce a reconciliation report that shows what did not map.
  • One boring deployment. A small managed database and a container or static host. No Kubernetes for a tool with nine users.
  • One instrument. Log who did what and when. If it does not record changes, it is not ready.
If you cannot describe it in one sentence, it is not a tool yet. “Technicians log a job and a supervisor closes it” is a tool. “A unified operations platform” is a programme with a steering committee.

What you get for the effort

  • One place where the truth lives, instead of four copies with different dates.
  • Every change attributable to a person and a time.
  • Rules in code, so they run the same way on a busy Friday as on a quiet Tuesday.
  • Onboarding that is a link and a short guide, not a week of shadowing.
  • Answers to “how many, how long, how often” without a manual count.

None of that requires a large team. It requires a narrow scope and the discipline to keep it narrow until the first version is in use.

Build it small, then earn the next version

  1. Ship v1 in weeks. If the first release is a quarter away, the scope is wrong.
  2. Run both for one cycle. Keep the spreadsheet read-only, enter data in both, and reconcile at the end of the month.
  3. Retire the old one only when the numbers agree twice. Not when the app is “done” — when the evidence says it is.
  4. Add what you missed, not what you predicted. The second version should come from the first month of real use.

This is also the safest way to handle the person who built the spreadsheet. They are not the obstacle. They are the specification. Sit with them, write down the exceptions, and let the reconciliation prove the replacement is faithful before anyone takes their workbook away.

When not to build

Building is not always the answer, and pretending otherwise is how consultancies lose trust.

  • If a commodity product already does 90% at a price the business will pay, buy it. The remaining 10% is rarely worth a custom estate.
  • If the process is broken, fix the process first. Software makes a bad process faster and harder to change.
  • If nobody will own it after launch, do not start. An unowned tool becomes the next spreadsheet, with a login page.

Internal tools are not glamorous. They are the difference between a team that scales and a team that depends on one person’s memory. Pick the workflow that hurts most, scope it to one sentence, and ship the small one.
